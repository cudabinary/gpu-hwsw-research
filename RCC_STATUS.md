# RCC status

## DistanceGuard API experiment — 2026-10-21

**Experimental CPU substitution passed. Default RCC integration is on hold.** The unchanged MAIN binary, SHA-256 `d5238d6b796509e64cab143ac5c1d75cdf368c4aba2f7325c6e309ec7483862e`, passed all 11 substitutions across baseline BFS, TABLE, LAST, and four DistanceGuard variants in ready and deferred configurations. The service campaign passed 26,880 trials and 564,480 arrays, with independent Python validation. The analysis accounts for matched output-copy costs, algorithm and adapter work, and variation across five sessions. [DistanceGuard API results](research/DG_API_RESULTS.md)

The only condition meeting all criteria was synthetic `oneway_dense` with legacy sources at ready q32. DistanceGuard took 0.7331 times the matched TABLE time, with 37/40 wins and a descriptive bootstrap 95% interval of 0.7195–0.7672. With preparation, the ratio rose to about 1.31. With distinct sources and ready preparation it was 1.3117. The `bound < n` API restriction removes unique filter savings on Google, and the 48,273 fewer matched probes on LiveJournal still leave the guard slower than OLD_P2 and RIE. The campaign ended without further optimization, default integration, GPU work, or paid resources. Academic novelty and a standalone contribution remain unestablished.

RCC's zero additional work avoided after Direction+RIE remains a result of the earlier LiveJournal experiment.
